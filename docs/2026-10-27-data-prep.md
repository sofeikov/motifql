## 3. USD conversion

Median implied rate (received/paid) per currency pair over 72,170
mixed-currency rows / 201 pairs. Fiat pairs are near-exact
(p95/p5 ≈ 1.0001). Two Bitcoin pairs show wide spreads (USD→BTC 1.500 at
n=1,496; Yuan→BTC 1.667 at n=140) — but their daily medians are flat at
11,868–11,881 USD per BTC, so the spread comes from within-day outliers,
not drift, and medians are robust to them. Every pair therefore converts
with one global median.

Every payment currency reaches USD directly or via a short chain, so all
5,078,345 rows convert; none left null. `amount_usd` converts `amount_paid`;
originals are kept.

## 4. Pattern instances and the attribution gap

370 instances across all 8 AMLworld types; every one of the 3,209 pattern
lines joins to a transfer row on all original fields (footers
`END LAUNDERING ATTEMPT - ...` skipped).

The headline finding: only 3,209 of the 5,177 flagged laundering rows (62%)
are attributed to any instance. The 1,968 unattributed rows are not duplicates
or join misses — they are absent from `HI-Small_Patterns.txt` — and form a
distinct population:

- attributed: ACH only (3,208/3,209), accounts in the `8xx` block;
- unattributed: mixed formats (ACH 1,275, Cheque 324, Credit Card 206,
  Cash 108, Bitcoin 55), incl. a 633-row cluster at bank `070` / account
  block `100…`, plus ~1,335 diffuse rows; only 25 touch instance accounts;
- unattributed rows appear only on Sep 1–10; every tail-day flagged row
  (Sep 11+) is attributed.

Ground-truth policy for RQ1: recall-per-pattern over attributed transactions;
overall recall over the flag, reported with this caveat. The unattributed
population (especially the bank-070 cluster) is follow-up material for the
Nov 1 discovery agent.

The design's "10 days" are Sep 1–10; Sep 11+ is a thin synthetic rundown
(11–396 rows/day, mostly laundering) where per-day alert budgets are
meaningless. Split:

- warm-up: Sep 1–2 (history for trailing windows; 7d windows fill only
  partially before Sep 8 — accepted, documented);
- train: Sep 3–7 (~1.86M rows; agent/model fitting only);
- holdout: Sep 8–10 (~1.35M rows; never shown to any model);
- tail Sep 11+: kept in Parquet, excluded from scoring.

Day cutoffs would slice multi-day instances in two, so instances are
assigned wholly to one bucket by their member span (`eval/splits.py`):

| Bucket | Rule | n |
|---|---|---|
| train | wholly in Sep 3–7 | 84 |
| holdout | wholly in scored Sep 8–10 (completable) | 29 |
| holdout_partial | starts Sep 8+, runs into the tail, has scored members | 77 |
| crosser | spans a scored boundary (dropped from both sets) | 160 |
| warmup_only / tail_only | outside every eval set | 13 / 7 |

Per-instance recall is reported over holdout + holdout_partial (106), with
the completable-only subset (29) alongside. Transfer-level training labels
are unaffected: the buckets govern instance eval sets and agent-visible
instances, not rows.

## 6. Aggregate baselines

Three model rows, one shared protocol (`eval/features.py`, `eval/splits.py`,
`eval/evaluate.py`): 18 trailing-window features (count, distinct
counterparties, sum of USD over 1h/24h/7d, sender + receiver side; count/sum
via cumulative sums plus as-of window starts, distinct via a linear sweep),
holdout transfers ranked per day, recall at fixed alerts/day budgets, at
transfer and instance granularity. Full rankings saved to gitignored
`data/hi-small/*_scores.parquet`, so any later budget applies with no
recompute. Machine-readable tables in `eval/results/recall_*.csv`
(generated locally, not committed).

- **unsupervised** (`eval/baseline.py`): each feature rank-normalised
  against the training distribution (no labels), score = max, ties broken
  by the second-largest value, then transfer id.
- **gbm / gbm_noformat** (`eval/supervised.py`): LightGBM on flag labels,
  fit Sep 3–6, early stopping on Sep 7 valid AUC, test Sep 8–10; 18
  features plus one-hot payment_format, and the same without format (see
  §7). One tree each (valid AUC 0.940 / 0.926): the learnable signal is
  coarse — account activity plus format — and deeper trees don't generalise
  to the valid day. Top gain features: `fmt_ACH` then counts for gbm;
  counts/sums for gbm_noformat.

distributions skew low — second-order for rank-only scoring, noted for both
baselines.

## 7. Shortcut policy (binding for motifs and the agent)

Two dataset shortcuts must not become results:

1. **Account and bank IDs are banned features** — in baselines, in motifs,
   and for the discovery agent. They separate populations by construction
   (pattern accounts live in the `8xx` block), and the AMLworld paper
   excludes them too. Neither baseline uses them.
2. **Payment format gets with/without reporting, not a ban.** ACH marks
   99.97% of pattern transfers against 11.8% of background (≈7× lift), and
   the gbm top feature is `fmt_ACH`. It is a legitimate field an analyst
   would use, so every RQ1 number is reported both ways: the baselines do
   this as gbm vs gbm_noformat rows, and each motif will later be evaluated
   with and without format conditions (harness switch to be built with the
   matcher).

Amounts stay allowed: flow conservation is the signal under test, not a
shortcut.

## 8. Deviations from DESIGN.md

- Prep uses Polars, not DuckDB (§6.1): agreed with owner; Parquet schema is
  the contract, DuckDB can be revisited for HI-Medium scale.
- Baseline windows are exact: count/sum via cumulative sums plus as-of
  window starts (Polars); distinct via a linear sweep (numba), because the
  sender side has 100K+ transfer hubs (bank 070), for which pair
  materialisation means tens of billions of pairs (measured; OOMs), and
  windowed distinct over such hubs has no window-function formulation. The
  numba dependency is forward-compatible with §6.2's named fallback.
- LI-Small not prepped (not downloaded; needed by Oct 30).
- Spark smoke test deferred (no model need on the data path; credits claim
  stays a manual parallel step).
- No single alert budget fixed; recall reported at 50/100/500/day with the
  full holdout ranking saved for any later budget.

## 10. Correction (Nov 1): ranking, features, GBM retrain

The §6 numbers mixed three bugs (issue #6, E1–E3): score ties broke by
`transfer_id`, which is file order and correlates with the label
(laundering rows cluster early in the day — a constant-0 scorer hit
706 transfers at 500/day); same-minute ties counted in file order in
the trailing features (laundering rows come last, inflating their
counts); and `scale_pos_weight=neg/pos` left each GBM a single tree
with 45/58 distinct scores. Fixed: ranking breaks ties by a keyed hash
of the id (deterministic, label-blind); features count strictly
earlier timestamps (file-order free, pinned by a shuffled oracle test);
GBMs train unweighted. Rerun on the same splits:

- **gbm**: 18 trees (was 1), valid AUC 0.976 (was 0.940); top gain
  features counts/sums, `fmt_ACH` fifth (was first). Scores are now
  ~continuous (17K distinct, none pinned at 1.0).
